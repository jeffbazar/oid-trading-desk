# OID per-bot model plan (synthesized recommendation), 2026-10-21

## Executive summary

**One rule decides every row below: the stakes of the output and its latency need pick the primary; the other path is the fallback.** Narrative and agentic work (Rose, Hal, Macro, Research, Post-Mortem, Gate Keeper) runs **API-primary on the Anthropic lineup** because nothing that fits a Mac matches it on tool use or long-horizon reasoning (Terminal-Bench 2.1: Qwen3.8-27B 73.0 vs Claude Opus 4.8 85.0, VERIFIED in the GLM README). Feature-grade classification (Peanut/News, X Summarizer) and low-stakes summaries (Data Ops, Earnings/IV, Chart captions) run **local-primary on the 64 GB mini** because a sha256-pinned GGUF with `--seed` and `-np 1` is more reproducible than any API model id, and the cost difference is a rounding error either way. **First-Seen is the exception: Haiku 5.5 stays primary** because its gate flags need ≤60 s at the open and a single-slot local 9B queues to ~16 min on a 100-item burst (Plan B arithmetic, UNVERIFIED).

**Disagreements between Plan A and Plan B, resolved:**

1. *Local standby cold (A) or resident (B)?* **Resident.** A cold load is an untested failure mode; instead the 35B-A3B instance is kept warm by giving it real but unimportant work (Data Ops, Earnings/IV) every hour, so failover is exercised daily.
2. *Research sandbox stays on the 64 GB mini (A) or moves to the 128 GB Mac (B)?* **Phase 1 stays; Phase 2 moves.** The 128 GB Mac is not needed to launch. It becomes necessary the first time a research job needs more than the ~15 GB left after serving, or when you want gpt-oss-120b as a narrative failover. That trigger, not a date, brings it online.
3. *Serving stack for narrative: mlx_lm.server (B) or llama-server (A)?* **llama-server for everything in Phase 1.** One stack to operate, and it is the only one where JSON-schema/GBNF, continuous batching, `--jinja` tools, `--seed`, prompt cache and `/metrics` are all VERIFIED in the official README. Move narrative traffic to vllm-mlx only if a measured Rose failover call exceeds 60 s.
4. *Classifier primary: API (A) or local (B)?* **Split by stakes**, as above, and gated: no local instance becomes primary until it passes the 200-item gold set, re-run agreement and a latency SLO. Haiku 5.5 is the launch primary for all three; Peanut/X migrate to local when the gate passes.
5. *Owner Mirror on gpt-oss-120b (B) or Sonnet Batch (A)?* **Sonnet 5.5 Batch** at ≈ $0.60/month; the 128 GB box does not need to earn its keep on that job.
6. *Peanut/X model: 9B (A) or 4B (B)?* **9B in Phase 1 (one instance serves all three classifiers in shadow); add the 4B in Phase 2** when Peanut/X go local-primary and need ~2 s/item at the open.

Expected bill: **≈ $150–$320 per month**, of which the research loop is 60–80 %; the rest of the desk is ≈ $55–$65. The hardware already owned runs the local path for ≈ $15–$25/month of electricity (UNVERIFIED estimate). The order path never touches a model.

## 4. Determinism and governance

**Every LLM feature is a versioned, scored numeric feature.** A feature call is identified by

`feature_id = sha256(prompt_template || json_schema || tool_defs || model_pin || decode_params || server_pin)`

where `model_pin` is the exact API id (`claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5-5`, `claude-fable-5-1`; never an alias) plus the `model` string echoed in every response so a silent server-side change surfaces as a diff; for local calls it is the sha256 of the GGUF file, the quant tag (`Q8_0`, `Q4_K_M`), the llama.cpp commit and the `-c` context size. `decode_params` is `temperature=0`, `top_p=1`, `max_tokens`, and for local calls a fixed `--seed` with `-np 1` so the request never shares a batch. Research 2 shows greedy decoding still drifts with batch composition (Thinking Machines: ~80 distinct completions of 1,000 at temp 0 on default kernels, EXTRACT) and no batch-invariant mode exists for Metal or MLX, so single-sequence execution is the only lever available on a Mac. Narrative calls on B may batch because they are not features.

**Every row logs** `feature_id`, `source` (api / local / local_fallback / api_fallback), full rendered prompt, raw response, `usage`, latency, and for classifiers the deterministic check that `evidence_quote` is a verbatim substring of the input. Proprietary calls use `output_config.format` with a strict schema; local calls use `json_schema`/GBNF so the schema is enforced regardless of model (Research 1's structured-output note).

**Re-run agreement is a first-class metric.** A 50-item replay runs weekly on mini #3 (local) and against the API: target ≥ 0.99 for enum fields, ≥ 0.95 for free-text fields. Below floor the feature is quarantined, not silently drifted. API agreement is measured, not assumed.

**Model swap = code change.** A new model file, quant, server version, prompt wording, schema field or API id produces a new `feature_id` and enters the same promotion ladder as a commit: (1) shadow for ≥ 5 trading days producing a parallel column the ranker does not read; (2) gold-set precision at or above floor and re-run agreement at floor; (3) correlation and label-drift report against the incumbent column, reviewed by Opus 5.5 for Gate Keeper proposals; (4) promotion flips the one `feature_version` named in config, with the old column retained 30 days for rollback; (5) the swap is recorded in the config repo with sha256 and gold-set report attached. API deprecations follow the same path: the old id stays pinned until the new id passes. Gate Keeper can only *propose* the diff.

**Gold-set evaluation (First-Seen, Peanut/News, X Summarizer).** One 200-item stratified set per classifier (First-Seen: ≥ 30 per gate flag plus 60 negatives), labelled by two independent judges (owner plus Sonnet 5.5 at temp 0; disagreements adjudicated by the owner; the Pugnola dual-judge template is the pattern, UNVERIFIED source). Stored outside the sealed holdout, readable only by the harness user, never by the research loop. Reported per model: per-flag precision and recall, macro-F1, confidence calibration (ECE in 5 bins), evidence-quote validity, re-run agreement, and p95 latency at the open. Floors: First-Seen per-flag precision ≥ 0.95, highest on `halt` and `earnings` because they feed Event Gate; Peanut/X macro-F1 ≥ 0.70 and no worse than FinBERT on the same set. Refresh 40 items per quarter from live traffic, keeping the old 200 as a regression set. **This applies to Haiku 5.5 too**: it is the launch primary because it is the reference's small fast model, not because it is assumed to pass. Published benchmarks (τ2-bench, BFCL, FPB) shortlist only; FinBERT's 0.64 on live headlines is the cautionary number.

## 6. What not to do

1. **No LLM in the order path.** Surge engine, ranker, contract selector, sizing, exits, risk sentinel, gateway and reconciler consume logged, versioned feature columns and configs only; a First-Seen flag is an input to the deterministic Event Gate, never an order trigger; an outage changes feature values, never order logic.
2. **No 8 GB mini hosts a model the desk depends on.** Usable model+KV on them is ~5–6 GB with swap risk and ~15 tok/s (UNVERIFIED); Gemma 4 E4B under Ollama already needs 7–8 GB on a 16 GB mini (EXTRACT). Minis #1–#4 run deterministic Python, the ≤ 1 GB FinBERT/SetFit encoder, monitoring, and the shadow 4B that nothing reads.
3. **No model without a measured precision on the gold set**, Haiku 5.5 included.
4. **No unpinned ids, no temperature above 0, no shared-batch decoding, no prompt edits outside the promotion ladder** for any feature call. A call that cannot be reproduced is not a feature.
