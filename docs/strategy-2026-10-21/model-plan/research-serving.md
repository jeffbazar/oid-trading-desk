## 1. Serving stacks (state as of 2026-10-21)

### 1.1 MLX / mlx-lm (`mlx_lm.server`)
- Latest release **v0.32.2 (2026-10-16)**; v0.32.0 (10-15) added MiniCPM5 tool parser, nvfp4 MoE global scale; v0.31.3 (04-22) "Fix parallel tool call handling in server"; v0.31.2 (04-07) "Caching system prompt and user messages for non-trimmable caches", "Batch generator refactoring", "Fix output corruption in speculative decoding"; v0.31.0 (03-07) "Better caching in the server", `usage.prompt_tokens_details.cached_tokens`; v0.30.4 (01-19) "Add a server benchmark for continuous batching". **VERIFIED** https://github.com/ml-explore/mlx-lm/releases
- **Continuous batching is built in** (not just via wrappers): `server.py` has a request `Queue`, a generation `Thread`, and mlx-lm's `BatchGenerator`; new requests join the running batch via `insert_segments`. Flags: `--decode-concurrency` (default **32**, "When a request is batchable then decode that many requests in parallel"), `--prompt-concurrency` (default **8**), `--prefill-step-size` 2048, `--prompt-cache-size` 10 ("Maximum number of distinct KV caches to hold in the prompt cache"), `--prompt-cache-bytes`, `--kv-bits` (4/8; "disables batching"), `--kv-group-size` 64, `--draft-model` + `--num-draft-tokens` 3, `--temp` default **0.0**, `--max-tokens` 512, `--pipeline`, `--allowed-origins`. **VERIFIED** https://raw.githubusercontent.com/ml-explore/mlx-lm/main/mlx_lm/server.py
- A request is **not batched** (served alone) if: a draft model is loaded, a per-request `seed` is set, `--kv-bits` is set, the model's cache lacks `merge`, or the message has images. `_is_batchable = model_provider.is_batchable and args.seed is None and cli_args.kv_bits is None`. Seed reseeds the global RNG (`mx.random.seed`). **VERIFIED** (same file)
- **Prompt cache**: `LRUPromptCache` with `fetch_nearest_cache(model_key, prompt)` prefix reuse; caches stored at end of system/user/assistant segments and after completions. **VERIFIED** (same file). Offline: `mlx_lm.cache_prompt` → `.safetensors` → `--prompt-cache-file`. **VERIFIED** https://github.com/ml-explore/mlx-lm
- **Structured output: none.** `handle_chat_completions` reads only `messages`, `tools`, `role_mapping`; no `response_format`/`json_schema`/`grammar` handling. **VERIFIED** (server.py). Tool calling: per-tokenizer `tool_parser` via `ToolCallFormatter` (Qwen3, Gemma 4, Mistral, Kimi, GLM 4.7, MiniMax M2, LFM2, MiniCPM5, LongCat parsers in release notes). **VERIFIED**
- Official docs: "The MLX LM server is not recommended for production as it only implements basic security checks." OpenAI-style `/v1/chat/completions`, `/v1/models`; per-request `draft_model`, `adapters`, `logprobs`, penalties. **VERIFIED** https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/SERVER.md
- Quantization: `mlx_lm.convert -q`; MLX-community Hub models in 4/6/8-bit affine, nvfp4/mxfp4 MoE support in v0.32.0. **VERIFIED** (README + releases). Distributed inference via `mx.distributed` (server supports it since v0.30.6). **VERIFIED**
- Known hazard: issue #883 "mlx_lm.server causes macOS kernel panic (IOGPUMemory crash) due to unbounded memory growth" (M3 Ultra 96 GB, macOS 26.3, Qwen3-Coder-30B-A3B-8bit, wired 80.14 GB = 83.5%); reporter says server "starts by wiring ~75% of RAM" via `set_wired_limit(max_recommended_working_set_size)` (maintainers did not confirm the figure); maintainer: "the panic is probably related to the wired limit being too high"; closed 02-19 via PR #906 but repeat reports on macOS 26.4 (03-31) and a `--kv-preallocate-size` PR #1920 (Sept 2026). **VERIFIED** https://github.com/ml-explore/mlx-lm/issues/883 → set `--prompt-cache-bytes` and keep the wired limit below RAM.

### 1.2 llama.cpp / `llama-server` (GGUF)
- `-np, --parallel N` "number of server slots (default: -1, -1 = auto)"; `-cb, --cont-batching` "(default: enabled)"; `-kvu, --kv-unified` "single unified KV buffer shared across all sequences (default: enabled if number of slots is auto)". **VERIFIED** https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md
- **Structured output (strongest of all servers)**: completion API `json_schema` "Set a JSON schema for grammar-based sampling", `grammar` (GBNF); `/v1/chat/completions` `response_format` "supports both plain JSON output (e.g. `{"type": "json_object"}`) and schema-constrained JSON". **VERIFIED** (README + raw README)
- Tool calling: "Function calling / tool use for ~any model", "supported with the `--jinja` flag" (default enabled), `parallel_tool_calls` "only supported on some models". `/v1/responses` "works by converting Responses request into Chat Completions request". **VERIFIED**
- Speculative decoding: `-md, --spec-draft-model`; old `--draft` removed in favour of `--spec-draft-n-max` / `--spec-ngram-mod-n-max` (n-gram self-speculation, no draft model needed). **VERIFIED**
- Prompt cache: `--cache-prompt` (default enabled), `--cache-reuse N` (KV shifting), `--slot-save-path` + `POST /slots/{id}?action=save`. Observability: `--metrics` Prometheus endpoint, `/slots` (per-slot speed, tokens, sampling params). `--seed` (default -1 random), `--temp` default 0.80. Slots only batch together when configs (e.g. LoRA) match; server loop is single-threaded. **VERIFIED** (README, README-dev)

## 2. Unified memory, wired limit, headroom
- MLX `set_wired_limit`: "only useful on macOS 15.0 or higher", "The wired limit should remain strictly less than the total memory size", "Setting a wired limit larger than system wired limit is an error", raise system limit with `sudo sysctl iogpu.wired_limit_mb=<size_in_megabytes>`; query with `device_info()` keys `max_recommended_working_set_size`, `memory_size`. `set_memory_limit` default = 1.5× recommended working set; cache limit defaults to memory limit. **VERIFIED** https://github.com/ml-explore/mlx/blob/main/python/src/memory.cpp
- Default GPU-wireable fraction: `iogpu.wired_limit_mb = 0` means system default; community sources put it at ~2/3–3/4 of RAM (≈48 GB on 64 GB); mlx-lm #883 reporter says ~75%. **No Apple documentation of the fraction found** → **UNVERIFIED** https://github.com/ivanopcode/devnote-override-macos-metal-vram-cap , https://mehmetbaykar.com/posts/increase-vram-apple-silicon-local-llm/ , https://github.com/ml-explore/mlx-lm/issues/883 . Setting does not survive reboot (re-apply from a LaunchDaemon). Older OS used `debug.iogpu.wired_limit` in bytes. **UNVERIFIED**
- Headroom rule used below: OS + services ≥ 8 GB on 64/128 GB boxes, ≥ 4 GB on 8 GB boxes; never wire >~88% of RAM (the #883 panic was at 83.5% wired with 0.01 GB free). Memory pressure check: `memory_pressure` CLI / Activity Monitor; yellow/red = swapping = inference collapse. **UNVERIFIED** (community guides) https://hometechops.com/mac/mac-mini-local-ai-server-ram-sizing
- Note: the current M4 Mac mini starts at 16 GB (M4 120 GB/s; M4 Pro 273 GB/s, 16- or 20-core GPU). Your 8 GB minis are therefore M1/M2-era (≈100 GB/s). **EXTRACT** https://www.apple.com/mac-mini/specs/

## 5. Determinism
- Temperature 0 (greedy) removes sampling noise but not numeric noise: Thinking Machines "Defeating Nondeterminism in LLM Inference" (Horace He, 2025-09-10) attributes run-to-run drift to batch-dependent kernels (RMSNorm, matmul, attention); default Qwen run gave ~80 distinct completions of 1,000 at temp 0, batch-invariant kernels gave 1. **EXTRACT** https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference (secondary: https://www.outlookbusiness.com/deeptech/artificial-intelligence/why-ai-chatbots-give-different-responses-for-same-prompts-and-how-engineers-can-fix-it)
- vLLM's `VLLM_BATCH_INVARIANT=1` exists only for NVIDIA ≥8.0, AMD Instinct, Intel XPU — **not Metal/MLX**. **VERIFIED** https://github.com/vllm-project/vllm/blob/main/docs/features/batch_invariance.md . No batch-invariant mode found for llama.cpp Metal or MLX (**UNVERIFIED** absence; llama.cpp commit #4668: temp>0 + seed is deterministic, batched decoding regression #6173 shows batch composition affects numerics).
- Practical recipe for feature-grade calls: `temperature:0`, fixed `seed`, same model file hash + quant + server version + context size, and **force single-sequence execution**: llama-server `--parallel 1` (or a dedicated instance), mlx-lm: send `seed` (routes to `_serve_single`, **VERIFIED** in server.py), Ollama `options.seed`. Log prompt hash + full response; treat the output as a scored feature with a re-run agreement metric rather than assuming bitwise identity.

## 6. Keeping a model resident 24×7
- launchd: `KeepAlive` "indicates that this job needs to be running at all times… launchd should always try to keep this job running"; daemons in `/Library/LaunchDaemons` run at boot; agents "execute only while that user is logged in"; don't exit within 10 s of launch or launchd may suspend the job. **VERIFIED** https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html → use a **LaunchDaemon** (headless mini, no login) with `RunAtLoad`, `KeepAlive`, `EnvironmentVariables` (launchd doesn't read `.zshrc`), and a preceding daemon that applies `sysctl iogpu.wired_limit_mb`.
- Ollama app: `launchctl setenv OLLAMA_KEEP_ALIVE=-1` etc. then restart app; or run `ollama serve` under your own LaunchDaemon. **VERIFIED** faq.mdx. llama-server and mlx_lm.server keep weights loaded for process lifetime; oMLX via `brew services` with auto-restart. **VERIFIED**
- Power: `sudo pmset -a disablesleep 1`, weekly reboot cron; watch `memory_pressure`; mlx-lm bound `--prompt-cache-bytes`, llama-server bound `-c`×`-np`. **UNVERIFIED** (community) https://www.popularai.org/p/run-local-llm-mac-mini-m4

## 8. Recommended stack
1. **Primary server for typed/feature calls (First-Seen, X Summarizer, Peanut/News scoring, Chart features, Data Ops summaries): `llama-server` (GGUF)** — the only stack where JSON-schema/GBNF constrained output, continuous batching, `--jinja` tools, `seed`, prompt cache, `/metrics` and `/slots` are all **VERIFIED** in the official README and mature. Run two instances per box: `-np 1 --temp 0 --seed N` for feature-grade determinism, `-np 4..8 -cb` for narrative traffic. Accept ~20–40% lower decode than MLX for the guarantees.
2. **Secondary MLX path for throughput on narrative/reasoning bots (Rose rationale, Hal, Macro, Owner Mirror, Post-Mortem):** `mlx_lm.server --decode-concurrency 8 --prompt-concurrency 2 --prompt-cache-bytes <budget>` (built-in continuous batching + LRU prefix cache **VERIFIED**); if you need schema enforcement on MLX, use **vllm-mlx** (lm-format-enforcer **VERIFIED**) or **oMLX** (EBNF/regex/JSON grammars **VERIFIED**), accepting younger codebases.
3. **Do not** put bots behind Ollama's MLX runner while #17280/#17317 stay open (requests serialize); Ollama-with-GGUF works but adds nothing over llama-server. LM Studio/llmster is a reasonable closed-source alternative to (1)+(2) if you want a GUI; its MLX+schema+batching combo is **UNVERIFIED**.
4. Model placement: 30B-A3B-class MoE (Qwen3.5-35B-A3B or Qwen3-30B-A3B, 4-bit ≈18–20 GB) is the fleet workhorse (4–9 s per call); a 100B-class MoE (gpt-oss-120b MXFP4 ≈60 GB) only on the 128 GB Mac; dense 30B only when quality justifies ~30–40 s per call. Research Bot code/review and Post-Mortem can stay on Claude Opus 5.5 / Sonnet 5.5 per the report; Haiku 5.5 remains the cheap cloud fallback for classification if local precision floor isn't met.
5. Measure before committing: `llama-bench -p 2048 -n 300`, `mlx_lm.benchmark`, `vllm-mlx bench-serve` on your own units; all 2026 M4 numbers above are community-submitted.
